How it works

How GPS and IMU are fused in a Kalman filter, and how that filter predicts one second ahead.

getting startedhow it worksreadme

A GPS receiver tells you where you were, about once a second, give or take a few metres. An IMU tells you how you are accelerating, a hundred times a second, but integrating it drifts away within seconds. A Kalman filter combines the two strengths: the IMU carries the state smoothly between fixes, and each fix pulls it back to the truth. Once you have a good position and velocity, plus the recent measured acceleration, predicting one second ahead is a matter of running the motion model forward without a measurement.

the state

x = [ east, north, up, v_east, v_north, v_up ] (UTM grid of the first fix, metres)

P, a 6×6 covariance, holds how sure the filter is about each element and how the elements correlate. NMEA has no vertical velocity, so v_up is learned only from the accelerometer and from successive altitudes.

one cycle

predict, on every IMU sample (100 Hz)

The IMU acceleration, already rotated to east/north/up with gravity removed by the shared xbus library, then rotated by the grid convergence into UTM-grid axes, is the control input of a constant-velocity model:

p ← p + v·dt + ½·a·dt² v ← v + a·dt Q per axis = σ²·[ dt³/3 dt²/2 ; dt²/2 dt ] σ smaller with imu, larger without

Q is the uncertainty added because the acceleration is not known exactly. Without an IMU the filter still runs, but with a larger σ standing in for unknown manoeuvres.

update, on every GPS fix (1 Hz)

  1. Position (+ altitude). σh scales with the HDOP (with a floor), and σv is a multiple of σh, because receivers are worse vertically. Without an altitude in the fix, only east/north are updated.
  2. Gate. The normalised innovation squared is compared to a χ² threshold for the measurement's degrees of freedom. A fix outside it is rejected as a glitch. After several rejections in a row the filter assumes that it is the one that is wrong, and restarts from the GPS.
  3. Velocity. Speed and course become a horizontal velocity measurement (course rotated from true to grid north). At very low speed the course is meaningless, so a slow fix is used as “zero velocity” instead.

the prediction

predict_ahead(t) copies the filter and runs the predict step once over t seconds, with no update. For the acceleration it uses the recent IMU acceleration, low-pass filtered so one noisy sample does not throw the ghost off. The copied covariance grows with t, so the returned σ tells you how much to trust the prediction.

The model assumes acceleration stays constant for the next second. That is why the worst predictions (the p95 column) happen at the start of turns and speed changes: the drone has started doing something the recent acceleration did not show.

why it should beat raw GPS

The filter averages GPS noise over many fixes, weighted by how consistent each one is with the IMU motion, and it knows the acceleration, which a fix alone cannot. Altitude is expected to be the hardest axis: it is the noisiest measurement and the only one with no velocity measurement. The simulation prints its own comparison (ghost vs. raw GPS extrapolated, estimate vs. raw fix) when you stop it. Accuracy results are not documented yet while the tuning is in progress.

the simulation

sim/worlds/positioning.sdf has a real multirotor model. It tilts to accelerate, so the IMU orientation and gravity removal are exercised the same way as on hardware. positioning_sim connects to Gazebo:

topicbecomes
/drone/imu 100 HzXbus sample with added bias, tilt and heading error → add_imu_sample
/drone/navsat 1 Hzgps_fix with white noise + drift → add_gps_fix
/model/drone/poseground truth, used only for scoring
/drone/cmd_velthe bridge flies the figure-eight here (unless --manual)

Each ghost is stored with its target time. When the simulation reaches that time, the ghost is compared to the true pose. That comparison is the error you see. The same position_estimator class runs in src/main.cpp on the device. Only the inputs differ.
